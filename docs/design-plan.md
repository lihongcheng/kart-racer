《极速小车》设计方案与开发计划

编写日期：2026-10-01。用户确认后已按本方案实现首个可玩版本，启动方式见 [README](../README.md)，实测结果见 [验收记录](validation.md)。

实施状态（2026-10-01）：

- 已实现 P0–P4 的核心范围：PC 键盘驾驶、漂移与氮气、1+5 三圈竞速、两档 AI、计时练习、车库配色、教程、HUD、音效、本地成绩与资产工作台。
- 已通过 OAuth MCP 生成并接入赛车车身、棕榈、岩石三件真实 Rodin 模型。生成任务及来源见 `assets/manifest.json`。
- 已实现 Fastify + SQLite 任务服务，REST 生成使用可选 `RODIN_API_KEY`；OAuth MCP 的既有模型可以直接运行，无需额外密钥。
- P5 已完成规则/服务测试、浏览器连续 10 局自动驾驶完赛与实际键盘操作验证。完整比赛自动驾驶结果不等同于人工手感验收。
- 简化实现：车辆高度用赛道样条投影，Rapier 处理车辆/护栏碰撞；驾驶员与独立轮组用代码建模；当前未做远景 LOD、骨骼动画和约五类 Rodin 装饰全量制作。新生成资产先在工坊预览/下载，自动装备不在本版。

以下保留原始方案与阶段估算，工程目录以实际代码为准。

建议制作一款具有《跑跑卡丁车》式漂移、集气、氮气加速体验的原创 3D 街机竞速游戏，暂名“极速小车”。首版采用浏览器运行，PC 键盘优先，移动端横屏触控适配安排在后续版本。项目目录为 `games/kart-racer/`。

以下平台、规模和美术主题已用于首个可玩版本。

1. 产品定位与首版范围

目标体验：打开网页后快速开始比赛，通过漂移积攒氮气，在容易理解的赛道上与 AI 竞速，约 3–5 分钟完成一局。

| 项目 | 首版设计 |
| --- | --- |
| 视觉风格 | 明亮卡通、圆润车身、清晰道路边界；原创角色和车辆 |
| 赛道 | 1 条“海岛环线”，包含直道、连续弯、发卡弯和缓坡；没有交叉立交 |
| 参赛车辆 | 1 名玩家 + 5 名 AI |
| 比赛规则 | 3 圈竞速，支持简单与普通难度 |
| 赛车资产 | 1 款主赛车，3 种配色；配色共用驾驶参数 |
| 模式 | 快速竞速、计时练习 |
| 核心操作 | 加速、刹车、转向、漂移、氮气、复位、暂停 |
| 记录 | 本地保存最佳圈速、完赛时间、音量和画质 |
| 后续扩展 | 道具赛、更多赛道、手机触控、多人联机、玩家生成赛车外观 |

首版验收围绕完整单人比赛及真实 Rodin 资产接入。多人联机涉及权威服务器、同步、匹配与作弊校验，应独立规划。

2. 玩法与交互

完整流程为：主菜单 → 选择车身配色与模式 → 新手操作提示 → 倒计时 → 比赛 → 成绩结算 → 重赛或返回。

| 输入 | 功能 |
| --- | --- |
| W / ↑ | 加速 |
| S / ↓ | 刹车，低速时倒车 |
| A、D / ←、→ | 左右转向 |
| Shift + 转向 | 达到最低速度后进入漂移 |
| Space | 使用一罐氮气 |
| R | 返回最后有效安全位置，并施加时间代价 |
| Esc | 暂停/继续 |

漂移设计采用“进入—保持—释放”状态机。玩家在弯道中保持有效侧滑可积攒氮气；低速原地打转、撞墙和停驶不计集气。释放漂移后根据有效持续时间给予短暂小喷。氮气最多保存两罐，使用时消耗一罐；持续时间、加速度、集气阈值集中在配置中，由试玩调整。

HUD 展示名次、圈数、速度、计时、氮气槽、迷你地图和下一处弯道提示。漂移提供轮胎烟雾、胎痕和音效；氮气提供尾焰和适度视野变化。镜头跟随位置做平滑处理，晃动可以关闭。

碰撞产生速度损失与轻微反弹。驶出道路后降速；翻离赛道、长时间卡住或主动复位时，恢复至已通过检查点附近的空闲安全位置。切出页面自动暂停并清空输入，避免返回时出现时间跳跃或按键卡住。

3. 技术架构

| 层 | 选型 | 职责 |
| --- | --- | --- |
| 页面与工程 | React + TypeScript + Vite | 菜单、设置、车库、结算页、构建 |
| 游戏渲染 | Three.js | 场景、相机、模型加载、灯光、粒子 |
| 车辆与碰撞 | 自定义街机车辆控制器 + Rapier 3D | 控制加速与侧滑，完成车体碰撞、地面检测 |
| 比赛系统 | 独立 TypeScript 模块 | 倒计时、检查点、圈数、排名、AI、复位 |
| 持久化 | localStorage | 小规模本地成绩与设置 |
| 资产制作服务 | Node.js + Fastify + SQLite | Rodin 凭据、任务记录、轮询、下载和资产登记 |
| 模型处理 | glTF Transform；必要时 Blender | 缩放、轴向、网格修整、压缩、LOD |
| 交付 | 静态游戏包 + 独立资产服务 | 游戏加载发布好的 GLB；资产服务供开发维护使用 |

游戏采用固定 60 Hz 仿真、渲染插值和追帧上限。每帧位置及速度直接更新游戏对象，React 只订阅低频 UI 状态，避免逐帧组件重渲染。

车辆采用动态简化碰撞体与地面射线检测，通过自定义动力、侧向摩擦及偏航控制实现街机手感。生成模型作为视觉子节点，不直接用高精度模型进行动态碰撞。先在平地和缓坡验证控制器，再扩展赛道。

赛道由中心样条、宽度和高度参数生成道路网格，同时维护道路边界、安全复位点、AI 路径与有序检查点。排名依据有效圈数、检查点序号及当前路段进度计算。必须顺向依次通过检查点才能计圈，防止倒车过线、抄近路或复位重复计圈。

AI 使用前视目标点跟随路径，依据曲率预判减速，通过不同目标速度、线路偏移和失误概率体现难度。AI 使用与玩家相同的运动及碰撞规则，卡住时通过统一复位流程恢复。

4. Hyper3D Rodin 接入

Rodin 负责生成车身、静态驾驶员及场景装饰。可行驶道路、碰撞体、检查点、导航路径和可旋转车轮由工程侧单独制作。模型生成结果需要导入检查，不假定自动具备可用拓扑、独立车轮或动画骨骼。

首版接入形态是开发用资产工作台：输入模型描述 → 选择生成配置 → 提交任务 → 查看阶段状态 → 下载与预览 → 优化 → 登记资产版本 → 游戏引用。资产工作台本地运行；如果后续开放到网络，生成入口需增加管理员鉴权与用量限制。

比赛运行时直接加载已经验收的资产。生成服务不可用时，已发布游戏仍可运行。

经官方文档核实，API 基址为 `https://api.hyper3d.com/api/v2`，使用 Bearer 认证，流程如下：

| 步骤 | 官方接口 | 参数与处理 |
| --- | --- | --- |
| 提交 | `POST /rodin` | multipart/form-data；文本 `prompt` 或图片 `images`；请求 GLB |
| 查询 | `POST /status` | JSON 传入生成响应中的 `jobs.subscription_key` |
| 下载 | `POST /download` | JSON 的 `task_uuid` 取生成响应顶层 `uuid` |

当前官方 Quick Start 使用 `tier=Gen-2.5-Medium`，官方 API 页面也展示 Gen-2。模型档位、质量和网格模式作为服务端配置，实施时根据账号实际可用档位核验，不将文档示例视为已经获得权限或余额证明。

轮询在提交后至少 5 秒开始，逐步退避到最多 30 秒，并遵守 `Retry-After`。只有非空 jobs 列表全部为 `Done` 才进入下载；任一 `Failed` 则记录失败原因。设置可配置的总等待期限；本地超时不代表供应商任务已取消，也不自动再次提交付费生成。

生成响应顶层 `uuid` 与 `jobs.subscription_key` 必须分别持久化。任务创建使用本地请求标识避免重复点击；对结果未知的提交请求记录“待核实”，避免盲目重试导致重复扣费。服务重启后恢复已知任务的查询；记录供应商响应中的消耗量，实际单价与配额以账号和最新定价为准。

下载链接有时效，完成后应及时下载文件并保存至本地资产库或对象存储，游戏清单不保存临时签名链接。下载服务只对 Hyper3D API 请求携带 Bearer 凭据，下载模型时不向文件地址转发 API Key。

`RODIN_API_KEY` 只在资产服务环境变量中配置，不使用 `VITE_` 前缀，不进入前端代码、仓库或日志。

5. 资产清单及制作标准

| 资产 | 首版数量 | 制作方式 |
| --- | --- | --- |
| 卡丁车车身 | 1 款，3 配色 | Rodin 生成车身，工程侧处理材质及装配 |
| 驾驶员 | 1 个 | Rodin 生成静态卡通头盔驾驶员，必要时修整坐姿 |
| 车轮 | 1 套 | 单独建模，统一轴心，支持转向和滚动 |
| 场景装饰 | 约 5 类 | Rodin 生成棕榈树、岩石、看台等，通过实例化复用 |
| 道路及护栏 | 1 套 | 参数化网格和简化碰撞体 |
| HUD、迷你地图 | 1 套 | DOM/CSS 或程序绘制 |

车身提示词初稿：“Original stylized arcade kart chassis, rounded compact silhouette, turquoise and white paint, empty cockpit, no wheels, no driver, no text, no logos, clean game asset.” 提示词仅引导生成，车轮分离和几何结构仍需实际检查。

统一约定：米制尺度，Y 轴朝上，车辆局部 +Z 为前方，车身原点对齐底盘中心。导入适配层完成轴向转换和缩放，底盘、车轮挂点与视觉模型解耦。

模型验收检查纹理完整性、法线、车轮遮挡、座舱结构、轴心、缩放及材质一致性；先保存原始结果，再制作优化版本。模型确有缺陷时进行网格修整或有限重生成。

初始预算为工程目标，需按实测调整：

- 玩家整车含驾驶员约 20k–35k 三角形；远处 AI 使用约 5k–12k 三角形 LOD。
- 普通场景装饰约 0.5k–5k 三角形，重复物体实例化。
- 主车辆最多 2K 纹理，普通装饰优先 1K；按收益使用 Meshopt 与 KTX2。
- 首场比赛必要资源下载量争取控制在 20 MB 内；其余资源延后加载。
- PC 1080p 中画质以 60 FPS 为目标；中低档设备提供分辨率、阴影和粒子降级。性能报告必须记录测试机器、浏览器与画质。

6. 开发阶段与交付

按一名全栈开发者推进、账号可用且首版范围稳定估算，首个可玩版本约 12–15 个工作日；属于工作量预估，模型生成排队和美术返工可能延长日历时间。

| 阶段 | 估算 | 任务 | 交付与验收 |
| --- | --- | --- | --- |
| P0 技术验证 | 1 天 | 初始化独立工程；选定性能基线；验证 Rodin 提交、查询、下载 | 一件真实 GLB 在浏览器预览；确认使用档位及任务消耗 |
| P1 驾驶原型 | 2–3 天 | 简化测试赛道、加速、刹车、漂移、小喷、氮气、跟随镜头和碰撞 | 玩家可稳定过弯；30/60/120 FPS 下无明显速度差异 |
| P2 比赛闭环 | 2–3 天 | 三圈规则、检查点、排名、5 名 AI、复位、暂停和结算 | 完整跑完一场比赛；倒车、漏点、复位不能重复计圈 |
| P3 Rodin 资产与正式场景 | 3–4 天 | 资产工作台、任务恢复、模型处理、海岛场景、车辆装配 | 主赛车及至少两类场景模型来自真实 Rodin 输出；重启后任务可继续查询 |
| P4 体验完善 | 2 天 | 车库配色、迷你地图、教学、计时练习、音效、特效、本地纪录 | 首次进入能理解操作；刷新保留纪录；可关闭声音与镜头晃动 |
| P5 验收交付 | 2 天 | 资源压缩、画质档位、目标浏览器检查、异常恢复和部署说明 | 连续完成至少 10 局；记录帧率、加载时间、错误及修复结果 |

P0 尽早暴露 Rodin 账号、API 和模型导入问题；P1 优先验证驾驶手感；P3 在玩法闭环稳定后集中处理正式美术。关键节点分别交付可运行版本供试玩。

7. 验收方法与风险处理

比赛规则通过有意义的自动化用例验证：顺序检查点、错误方向过线、漏点、复位、排名和圈数边界。固定步长控制器用同一输入序列验证不同渲染帧率下的运动一致性。

资产服务使用模拟响应验证：任务失败、429 退避、空 jobs、下载链接过期、提交响应未知、服务重启恢复和缺失密钥。供应商实测聚焦一次完整小规模链路，不在自动化测试中反复生成付费模型。

手感、视觉遮挡、轮胎转动、AI 拐弯和音效通过实际试玩验收；性能以选定设备的测量结果为准，不把 60 FPS 目标表述为所有设备均保证达到。

主要不确定性是 Rodin 输出的可装配程度、街机漂移调参和浏览器资源预算。分别通过生成车身后独立装配车轮、先交付驾驶原型、模型 LOD 与纹理压缩处理。

规划阶段没有发起生成请求。实施阶段已使用用户授权的 OAuth MCP 完成三件真实资产的生成与下载。网页 REST 生成入口需要另外配置有效 API Key；当前该入口通过模拟响应验证，没有额外提交付费测试任务。

8. 后续版本

V1.1：横屏触控、自动油门、新赛道及幽灵车回放。

V1.2：道具赛，包括护盾、加速和干扰类道具，并单独调试平衡。

V2：多人房间与权威服务器，同步策略及服务器部署成本另行评估。

可选创作功能：玩家描述赛车外观，经 Rodin 生成、模型检测与优化后装备；外观与驾驶性能分离。该功能需要额外的账号、配额、排队和内容管理设计，不计入首版工期。
